# PHP2Shell

The shortcut this skill replaces: judging a host by `php -v` or a one-off grep over ssh. Ubuntu backports keep the upstream number (`8.3.6`) and carry the fix in the package revision, and a changelog read through `head | grep -q` under `pipefail` misses the CVE lines. The verdict for a branch comes from the audit records, never from a hand check.

Scripts live in `${CLAUDE_PLUGIN_ROOT}/scripts/`. Each run prints a human section plus records `@p2s schema=1 key=value ...`; the record format is defined in `scripts/lib/p2s.sh`.

Records name the SAPI in `sapi=`: `fpm` (PHP-FPM, service `php<X.Y>-fpm`), `apache2` (mod_php, service `apache2`), `cgi` (mitigation only). A branch served by both gets one record per SAPI, and each counts on its own.

## Steps

0. **Resume first**: `bash ${CLAUDE_PLUGIN_ROOT}/scripts/next.sh --latest` prints one `<host>: <step> - <reason>` line per host from the saved logs (steps `audit`, `investigate` = indicators of compromise, ahead of any fix, `fix`, `ensure`, `autoupdate`, `verify` = audit again after a write, `manual` = a branch whose release gets no free fix, or PHP outside dpkg, which only the operator can close, `done`). Take each host to the step it names; "no readable logs" means a fresh start at step 1.
1. **Audit** the hosts the operator names, all in one call: `bash ${CLAUDE_PLUGIN_ROOT}/scripts/run.sh audit <host>...`, host being an ssh alias or `user@address`. Read-only. Each host gets its own log in `~/.cache/php2shell` (survives the session); an unreachable or timed-out host is recorded and the run goes on, and the exit code is the worst host's. ssh runs with BatchMode, so a key that needs a passphrase and is not in the agent fails as `unreachable`: ask the operator to load it. When the permission layer denies the call, hand the operator the same line as a `!` command and read its output back. Done when every host has a log ending in a `run_end` record.
2. **Report**: `bash ${CLAUDE_PLUGIN_ROOT}/scripts/report.sh --latest` renders the newest log per host and mode. Show the operator the tables; an unreachable host has its own section with ssh's error. Done when every host from step 1 has a section. Then read each host's **Indicators of compromise** (`ioc` records, since `P2S_EXPLOIT_SINCE`, 2026-10-17): `crash` (segfaults of PHP or Apache in the kernel log, PHP-FPM signal 11, Apache AH00052, the "Allowed memory size ... Unknown on line 0" fatal), `shell_child` (a shell, `nc`, `curl`, `wget`, `python` or `perl` whose parent is a PHP worker or Apache, with its command), `new_php` (`*.php`, `*.phtml`, `*.phar` changed since the window under each web root and in `/tmp`, `/var/tmp`, `/dev/shm`; `capped=yes` means the count stopped at the cap). `next.sh` says `investigate` for any `shell_child`, or for crashes together with new PHP files. Tell the operator plainly: a positive result means the host may already be compromised, and the answer is to isolate and rebuild it and rotate every secret PHP handled there (database passwords, API keys, session and app secrets, TLS keys), not only `fix`; patching does not remove a web shell or un-steal a secret. A clean result is no proof: mtimes can be set back and logs rotated away. New PHP files alone are common after a CMS update: review them, do not conclude.
3. **Read the restart state of every `fixed` branch.** The verdict judges the installed package; a running PHP-FPM pool or Apache keeps executing the build it started with, so a host can report `fixed` and still serve the vulnerable code. The branch record's `restart` says which: `ok` (its service started after the newest package of the branch), `needed`, `not-running`, `unknown`. A mod_php record with `active=not-loaded` is installed but not loaded by Apache: it serves nothing now, and still gets the mitigation. Call a host protected only when every branch is `fixed` with `restart=ok` or `not-running`; `needed` goes to step 5, which restarts it.
4. **Ensure the mitigation** on every host where a `mitigation` record is not `mitigated`: hand the operator `! bash ${CLAUDE_PLUGIN_ROOT}/scripts/run.sh ensure <host>`, since it writes `99-security.ini` and reloads FPM pools and Apache. Read its log back and run step 2 over it. Exit 0: every web SAPI mitigated. Exit 3: name each blocker from the records, and leave the fix to the operator, because the files are theirs: an `override` record that `enables=yes` (file, line, and the pool for `sapi=fpm`; Apache config for `sapi=apache2`), a `foreign` 99-security.ini, a SAPI still `On` or `unknown`. Exit 1: a config test failed (`php-fpm -t`, or `apachectl configtest` for mod_php; the change was rolled back and the service kept running) or a reload failed; show the output. Done when every host's newest log shows each web SAPI `mitigated` or a named blocker.
5. **Fix** every host whose branch is `unfixed` or `restart=needed`: hand the operator `! bash ${CLAUDE_PLUGIN_ROOT}/scripts/run.sh fix <host>`, saying in one line what it changes (apt-get update, the pinned upgrade to each target, 99-security.ini, a restart of the touched pools and of Apache for mod_php). On a mod_php host also say that the patch runs a full `systemctl restart apache2`, which stops every Apache site on the host for a few seconds, so the first mod_php `fix` on a client server runs in a quiet window with the operator watching it live. The patch runs on the server as a transient systemd unit, so a dropped connection never stops apt; rerunning the same command attaches to a running patch or hands back a finished one, and never starts a second. Exit 0: fixed, HTTP codes unchanged. Exit 3: a branch has no fixed build in the lists (mitigated meanwhile) or a site's HTTP code changed; name which. The install runs under a temporary `/usr/sbin/policy-rc.d` (exit 101), so package maintainer scripts restart nothing before the worker's config test; a host's own policy-rc.d is kept in `/var/lib/php2shell/policy-rc.d.kept` meanwhile and put back. Exit 1: preflight stopped it (held package, changed Release info with the accept command, failed apt-get update, `reason=policy-rc-d`: a kept policy-rc.d could not go back, the output has the `mv` that does it), `state=rcd-failed` (policy-rc.d could not be put in place, nothing installed for that branch) or a config test or restart failed (`state=test-failed`: the new ini was removed and the service not restarted; `pool-down`, `apache-down`); show the output and the rollback lines. The package rollback line installs `/var/lib/php2shell/debs-<stamp>/php<X.Y>/*.deb`, the builds saved before the install (`apt-get download`, else `dpkg-repack`); a `rollback_debs` record with `missing=` other than `-` names packages that could not be saved, whose rollback relies on the archive still offering them: say so. The HTTP probe asks every nginx PHP site (`nginx -T`, https on 443) and every Apache vhost (`apachectl -S`) on its own port and address: https on 443, plain http on any other port, recorded as `name=<site>:<port>` off 443; `probe_summary state=no-sites` means neither dump named a site, so nothing was compared. Done when every fixed host gets step 0's `verify`, then an audit.
6. **Auto-updates** on every host whose audit has a `source` record (the ondrej/sury PPA) and `autoupdate ppa_covered=no`: hand the operator `! bash ${CLAUDE_PLUGIN_ROOT}/scripts/run.sh autoupdate <host>`, saying in one line what it changes (a pin file per distro-built PHP branch in `/etc/apt/preferences.d`, then the PPA origin in `/etc/apt/apt.conf.d/51php2shell-ppa-origins`) and what that commits the host to: the PPA has no security-only section, so unattended-upgrades will install every new PPA build of PHP (and any library the PPA ships) on its own schedule, restarting PHP-FPM as the packages install. The operator decides per host, with the client, whether that is acceptable; run it only on hosts the operator names after hearing this. The order is the safety: a PPA source whose Release info changed stops the run first (`stopped reason=release-info-changed`, nothing written; hand over the printed `apt-get update --allow-releaseinfo-change-<field>` after the operator checks the change); then the pins; then each installed PHP package's `apt-cache policy` candidate must keep the origin of its installed build (origin = the source apt-cache policy lists under the build), and every PPA build of a pinned branch must show a negative priority; only then is the origin written and checked with `unattended-upgrade --dry-run`. Only `ondrej/php` and `packages.sury.org/php` sources count. A host without the PPA gets nothing written. Read the `policy` records: `state=kept` per branch is the goal; `pin-ineffective` means a pin is in place and apt still picks the PPA build or shows a PPA build at a priority of 0 or more (`unheld=` names those packages; a preferences.d name apt skips, or another pin read first that outranks it), `would-change` means no pin covers the branch. Exit 0: configured or already in place (`keeper state=configured|unchanged`). Exit 1: `refused` (name the branch and the pin from the records; the pins stay, the origin was not written; the operator fixes the named file, then rerun), `dryrun-failed` (the origin entry was taken out again; `uu_dryrun result=distro-from-ppa` names in `from_ppa=` the distro-branch packages unattended-upgrades would take from the PPA), `interrupted` (the session dropped or was killed before the dry run's verdict; the entry was put back). A dropped session usually leaves no keeper record at all, the output being gone: ssh exits 255, and on the server the entry was put back (drop before the verdict) or kept or taken out by the verdict (drop during the dry run); rerun the same command to see which, `stopped` with `reason=no-cached-release` (`apt-get update` first), `release-info-changed`, `pin-write-failed`, `origin-write-failed` or `backup-failed`, not root. A file the keeper overwrites is kept in `/var/lib/php2shell/backup`; its rollback line is a `cp` back. A pin or origin already in place is recognised by content under any file name and not written twice. Done when every PPA host's newest keeper log says `configured` or `unchanged`, then step 0's `verify`.
7. **PHP outside dpkg.** A `foreign_php` record is a PHP no dpkg package owns: a running `php-fpm*`, `php-cgi*` or `lsphp*` by its `/proc/<pid>/exe`, a `libphp*.so` an Apache has mapped (`sapi=apache2`), or a binary in a known vendor path that nothing runs (`running=no`). `source` says whose it is: `cpanel` (EasyApache `ea-php`), `plesk`, `litespeed` (`lsphp`), `local` (a build under `/usr/local`), `unknown`. The version is information only, never a verdict: vendors backport fixes without changing it. Neither `fix` nor `ensure` touches it (both print "left alone"), and `next.sh` gives such a host `manual` instead of `done`. Name each path and its vendor's update route to the operator; the plugin cannot say whether it is fixed.
8. **Report the rest.** For each branch still `unfixed`, name the host, branch, reason and target. A target of `none` is a statement about the host's cached apt lists, never about whether a fix exists: when `lists_stale` is `yes` or `unknown`, say the lists predate the fixes (or are unknown). The two exceptions are `no-fix-for-release` and `fix-only-in-esm`: there the release itself gets no free fix, so never suggest `apt-get update`; name what closes it (Debian ELTS or TuxCare, the sury build of the branch, a supported release or branch; or attaching Ubuntu Pro ESM).

## Verdict reasons

| Reason | Meaning |
|---|---|
| `distro-threshold` | Ubuntu build at or above the fixed Ubuntu revision of the host's own release (`VERSION_ID`): Ubuntu fixes one branch on a different base per release (8.5: `8.5.4-0ubuntu1.5` on 26.04, `8.5.9-0ubuntu2.1` on 26.10), so a threshold never applies across releases |
| `upstream-threshold` | Upstream part of the version at or above the fixed upstream release |
| `changelog` | No threshold met, but the installed package changelog names both CVEs (vendor backport) |
| `below-threshold` | A threshold exists for this branch and origin, the build is below it, and the changelog does not name both CVEs |
| `no-cve-in-changelog` | No threshold for this branch (EOL: 7.4, 8.0, 8.1 from a PPA) and the changelog does not name both CVEs |

`cve_changelog=missing` means the `php<branch>-common` changelog is absent; treat the branch as unverified, which the verdict reports as `unfixed`.

## Targets

The audit judges the builds apt offers from the lists already on the host (it never runs `apt-get update`) and picks the target a patch would install. A target always keeps the installed build's origin: a PPA version can sort above a fixed Ubuntu revision and still be unfixed.

| Target reason | Meaning |
|---|---|
| `installed-fixed` | Nothing to install |
| `fixed-candidate` | The newest fixed build of the same origin that apt offers |
| `fixed-distro-build-not-in-cached-lists` | Distro build, and the cached lists hold no fixed distro build; a fixed PPA build does not count |
| `no-fixed-build-in-cached-lists` | PPA or other build, and the cached lists hold no fixed build of that origin |
| `no-fix-for-release` | Distro build on a release whose distro ships no fix at all (Debian 11: LTS ended 2026-08-31). Fresher lists will not help; `next.sh` says `manual` once the host is mitigated |
| `fix-only-in-esm` | Distro build on a release Ubuntu fixes only in Ubuntu Pro ESM (20.04, 18.04, 16.04, 14.04; USN-8948-2) and no `esm.ubuntu.com` source is enabled. With ESM enabled the normal candidate logic applies |

`lists_updated` is when the newest apt list of the branch's origin last changed; `lists_stale=yes` means it is older than the day the fixed builds came out, so the lists cannot contain one. Candidate records with `cve_changelog=download-failed` were judged by version thresholds alone.

## Host facts

The audit's last section tells the operator how to patch; report these alongside the verdicts:

- `pool used=no`: no nginx site points at the pool, so stopping it is an alternative to patching it. `used=unknown` (Apache running, or no readable nginx config) is never a stop candidate.
- `hold`: apt will not upgrade a held package; the patch waits until the operator releases it.
- `source release_info=changed`: the PPA changed its Release info (`changed=` names the fields), so `apt-get update` refuses that source and its lists stay stale until the operator accepts the change. `unknown`: no cached InRelease or the fetch failed.
- `autoupdate ppa_covered=no` on a host with a PPA source: PHP from the PPA never updates by itself; step 6 fixes it.

## Mitigation states

`session.upload_progress.enabled = 0` closes CVE-2026-115560 and the session path of CVE-2026-109619, whether or not a fixed build exists. Whatever is applied before PHP parses the request body decides: php.ini, `conf.d`, the pool config, and also nginx's `fastcgi_param PHP_VALUE`/`PHP_ADMIN_VALUE` and a `.user.ini` under the site's root, both of which can turn it back on per request (`.user.ini` verified on PHP-FPM 8.3.36 and 8.5.12, #31). Only `ini_set()` comes too late.

| State | Meaning |
|---|---|
| `mitigated` | The SAPI reports Off and no pool re-enables it |
| `override` | Something applied per pool or per request turns it back on, and the SAPI's `-i` cannot see it: a pool `php_value`/`php_admin_value`/`php_flag`/`php_admin_flag`, the same directive in Apache config for mod_php, nginx `fastcgi_param PHP_VALUE`/`PHP_ADMIN_VALUE` (`directive=PHP_VALUE`), or a `.user.ini` (`directive=user_ini`) |
| `foreign` | A 99-security.ini without the plugin marker or the legacy fix.sh comment; ensure leaves it alone |
| `not-mitigated` | The SAPI reports On |
| `unknown` | The SAPI binary gave no answer |

The Apache scan reads every file Apache's own include dump lists (`apachectl -t -D DUMP_INCLUDES`, so a custom `Include` counts); when the dump fails, `apache2.conf` and the `*.conf` files in `mods-enabled`, `conf-enabled` and `sites-enabled`. `.htaccess` files are not scanned, so a mod_php host with `AllowOverride` set can still re-enable upload progress per directory: say so when reporting such a host as mitigated.

For FPM, the scan also reads `nginx -T`: each `fastcgi_param PHP_VALUE`/`PHP_ADMIN_VALUE` that sets upload progress, with file and line from the dump, counted for the pool its server block's `fastcgi_pass` reaches (`pool=-` when it reaches no pool or sits outside any server block, as an included snippet does: then it counts for every FPM branch). It then searches each such server's `root` for `.user.ini` files (`user_ini.filename`), 4 levels deep and at most 200 files per root; `directive=user_ini_scan value=capped` means the cap was hit and deeper files went unread: say so. Neither nginx nor `.user.ini` files are edited; the operator fixes them, like pool overrides.

`ini=legacy` is a file written by the earlier fix.sh; ensure adopts it unchanged when it already turns upload progress off.

ensure also installs an apt hook (`/etc/apt/apt.conf.d/99php2shell-ensure` calling `/usr/local/sbin/php2shell-ensure`, log `/var/log/php2shell-ensure.log`), so a PHP branch installed later gets the mitigation without anyone rerunning ensure. The audit's `ensure_hook` record says `present`, `missing` or `outdated` (written by another plugin version or edited by hand); the last two send the host back to ensure. The hook never fails apt: its exit code is swallowed and its failures go to the log.
